# Nazar M2 - The House (all cameras, adaptive hero, controls, audio)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The home screen becomes the house: an adaptive hero (the camera that last saw motion takes the big tile at full quality), the other cameras below at low quality; a camera screen with drag-to-pan, privacy, quality and audio; everything live over WebRTC.

**Architecture:** Extends M1's server: a new MQTT subsystem feeds a motion-ordering service; the supervisor grows quality classes (hero high / tiles low); the control API ports the spike's proven command envelope with read-back. The web app grows the adaptive home and the camera screen.

**Tech Stack:** rumqttc (MQTT), axum (API), Svelte 5 (UI), go2rtc/WebRTC (already in M1).

**Spec:** `docs/design.md` §5 (live viewing) and §2 (MQTT is the event source). M1's contract: `docs/plans/2026-10-15-nazar-m1.md` (its pinned routes and types are consumed here unchanged).

## Global Constraints

- Same as M1: house Rust conventions, signed commits, branch `m2-house`, no scope beyond this milestone (recordings/notifications are M3 even though MQTT lands here - do not build them early).
- MQTT per spec §5: `ssl://mqtt.platform.quboworld.com:8883`, `username = <userUUID>`, `password = <live accessToken>`, subscribe `/monitor/<unitUUID>/#`; reconnect on token re-mint.
- The control envelope is the verified one (spike `control.py`): `PUT /unit-entity-management/api/v1/sp/{sp}/units/{unit}/entities/{entity}/devices/{dev}/command` with `{"topic": "/control/{unit}/{dev}/{service}", "payload": {"devices": {"deviceUUID": "{dev}", "services": {"{service}": {"attributes": {...}, "instanceId": 0}}}}}`. The camera ACKs everything 200 regardless of outcome - every write must be followed by a shadow read-back.
- PTZ attribute spelling is `horizontalVerticalPostion` (sic); privacy attribute is `camera_enabled` under report / `cameraFunction` for the write - copy the spike's working calls exactly.

## Review Focus

1. **Ack-lie writes**: PTZ/privacy responses say SUCCESS unconditionally - the API must return the read-back state, never the ack; a failed move must surface as a failed move - Task 2.
2. **Hero flapping**: motion events arrive in bursts from several cameras; the hero must not switch on every event - hysteresis (a challenger must be >15s more recent than the incumbent AND no switch within 30s of the last) - Task 1.
3. **Two sessions per camera**: hero (high) + tile (low) may coexist; the mint API's session rules (one session per request, `5001` session-exists on collision, per-session stream paths) must be handled, not hammered - Task 3.
4. **Drag runaway**: pointer drags emit many moves - the client throttles to max 4 writes/sec and the server bounds x/y to the camera's reported range - Task 5.
5. **Audio autoplay**: browsers require a user gesture for audible playback - the listen toggle IS the gesture; the stream starts muted and unmutes on the toggle, and the state is per-camera - Task 5.
