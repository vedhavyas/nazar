# Nazar M4+M5 - Desktop and Android (Tauri shells of the same web app)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The same Svelte app in Tauri shells: a self-updating macOS desktop app and a self-updating sideloaded Android APK, both pointing at the nazar server (default `nazar.hub`).

**Architecture:** No new app logic - the shells wrap the existing `web/` build. Forge Client's delivery pipeline is ported: same updater scheme (release manifest + signatures), same Android gradle-in-repo pattern, same justfile recipes.

**Tech Stack:** Tauri 2, tauri-plugin-updater, minisign, GitHub Releases, Gradle (Tauri android target), vitest untouched.

**Spec:** `docs/design.md` §8 (clients and delivery). Recipes to port (read them, then port, do not re-derive): /Users/vedhavyas/Projects/forge/justfile (`client-release`, `client-android-release`, `release`, `publish`), /Users/vedhavyas/Projects/forge/client/src-tauri/ (tauri.conf.json, updater config, gen/android/ layout, `UpdatePlugin.kt`), /Users/vedhavyas/Projects/forge/.github/workflows/ (release/image workflows).

## Global Constraints

- Same house conventions: signed commits, branch `m45-shells`, tauri.conf identifier `dev.vedhavyas.nazar`.
- The shells must not fork the web app: one `web/` source of truth; the shell differences live in `web/src-tauri/` and small platform shims only.
- Update artifacts: `latest.json` + binaries hosted on a dedicated PUBLIC `nazar-releases` repo's Releases (ruled 2026-10-16 - this repo is private and private release assets are not fetchable without auth, so the ported scheme would 404; the public posture matches the already-public GHCR image, the source stays private, and the WireGuard perimeter remains the access control). The updater endpoint is `https://github.com/vedhavyas/nazar-releases/releases/latest/download/latest.json`; `.sig` from a minisign keypair at `~/.tauri/nazar.key` (create if absent; the public key goes in tauri.conf; the private key rides nazar's CI secrets).
- Android: arm64-only APK, release-signed with `~/.android/nazar-release.keystore` (create if absent), `key.properties` gitignored; sideload instructions in the repo README.
- No secrets in the repo; no AI/process mentions in artifacts.

## Review Focus

1. **Server unreachable on first launch** (fresh install away from the mesh): the shell shows the server-address setup + a reachable-failure state, never a blank window - Task 4.
2. **Update loop gone wrong** (manifest pointing at a broken artifact): the updater must tolerate a 404/invalid manifest without bricking the app - Task 2.
3. **Android WebRTC/webview quirks**: Android System WebView must play the WebRTC stream; if a device's webview lacks the codec, fall back to the HLS path the M1 player selects - Task 3.
4. **APK signature mismatch on update**: updating over a differently-signed install fails - the release recipe must assert keystore consistency before publishing - Task 3.
5. **Settings persistence across the shells**: the server address must survive restarts on all platforms (localStorage in the packaged webview) - Task 4.
