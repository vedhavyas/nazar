# Nazar M6 - The Fast Lane (camera-direct P2P and talkback)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The camera-direct fast lane: live view and mid-session controls over the P2P/relay path once the server's genuine login earns the relay's arming - and talkback on top of it.

**Architecture:** The extracted reference client (Python, `reference/p2p_client.py`, with byte-exact capture vectors) is ported into the `qubo` crate as an engine the server can arm; its decrypted RTP feeds go2rtc as a stream source (the same delivery pipeline as everything else). The cloud mint stays as the fallback in the chain: fast lane -> cloudy.

**Tech Stack:** existing stack + tokio UDP tasks; byte vectors from `docs/qubo-protocol.md` and the pcaps.

**Spec:** `docs/design.md` §7 (the fast lane and talkback). The verification contract: `docs/qubo-findings.md` final verdict (relay arming is server-side, tied to genuine app-SDK sessions; the relay forwards a caller's SYN train to the peer's port - pairing is relay-initiated).

## Global Constraints

- Same as M1-M3 (conventions, signed commits, branch `m6-fast-lane`, no scope beyond this milestone).
- The reference client's wire behavior is the contract: port with its selftest vectors, byte-exact against `reference/p2p_client.py`'s expectations and the captured frames it cites.
- The fast lane is OPTIONAL at runtime: any arm failure falls back to the cloud path without disturbing the viewer; the engine must never wedge the supervisor.
- **Build order fold (2026-10-16):** the live-gated steps (Task 2's arm verification, Task 4's Step 3 acceptance) run in a lead-held session window; the lead watches for a genuine login and pings the builder when it opens. While the window is closed: Task 1 -> Task 3 -> Task 4's port and UI. Task 2 remains the milestone's kill switch.
- **Timeout interaction (folded 2026-10-16, re-review):** the supervisor's `arm_timeout` (15s default) bounds the WHOLE arm, while the engine's answer bound alone is 15s after allocation+token+srflx - so a slow or missing camera answer falls back to the cloud before the engine's relay-only continuation (finding 1's fix) can be reached through the server path. Deliberate: the product bound wins and the fast lane is optional; the arm EXAMPLE (no outer bound) is what reaches the relay-only leg for the verdict. The default stays 15s but is env-tunable (`NAZAR_P2P_ARM_TIMEOUT`) so the live wiring round can measure the real total without a rebuild.

## Review Focus

1. **Arm verification honesty**: Task 2's acceptance is an OBSERVED relay engagement on the server's socket (probe within ~1s of the register) - not "the code ran" - Task 2.
2. **Never wedge the pipeline**: arm failures, relay silence, and camera refusals all fall back to the cloud path within a bounded time; a viewer never sees a dead tile because the fast lane is trying - Task 3.
3. **Talkback audio doesn't leak into the wrong channel**: the mic uplink rides the P2P audio channel only; when the fast lane is down the talk button is disabled with a reason, never silently swallowing audio - Task 4.
4. **Control routing during a fast-lane session**: PTZ during an active P2P session rides the P2P data channel (2001 frames) like the official app; when the session ends the REST path resumes - Task 3.
5. **Resource bounds**: one fast-lane session per camera, one talkback per session; duplicate arms reuse, never stack - Task 2.

## Build deviations and rulings (folded 2026-10-16)

- **The armed-PTZ control frame (Task 3):** the captured command skeleton byte-for-key (wrapper, `devices.{deviceUUID, handleName, services}`, instanceId) with the inner write kept as the app's own absolute-move form (`attributes.horizontalVerticalPostion` + handleName, its C.a builder's shape) rather than the captured frame's `commands.<action>.parameters` (the directional-button form). Rationale: the UI is drag-to-absolute with an exact-landing read-back, which the directional form breaks; the skeleton is capture-pinned and the read-back surfaces a wrong guess as "not applied", never silently. If the live wiring round shows not-applied, the literal commands form is the first flip.
- **Fast-lane stream labels:** on the fast lane both the high and low labels read the same full-size camera stream (the shared template has no scale step; the cloud path's smaller rendition is mint-URL ffmpeg work with no P2P equivalent). Documented in fast_lane.rs; a per-name scale step only if the live round shows the tile's cost matters.
