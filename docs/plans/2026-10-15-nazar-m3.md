# Nazar M3 - The Memory (recordings and notifications)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Per-camera recording playback (cloud-allocated VOD sessions over the existing pipeline) and notifications (motion, camera offline, air quality) with snapshots, on the web app and both shells.

**Architecture:** Extends M2's supervisor with VOD streams (`vod-<device>`, idle-released) and M2's MQTT bus into a notification service with a recent-events store and WS push. Snapshot images are best-effort: the event feed's stored image when present, else a frame grabbed from a live pipeline at event time.

**Tech Stack:** existing stack; no new services.

**Spec:** `docs/design.md` §6 (recordings) and §5's notification decisions; M1+M2 plans' pinned routes/types consumed unchanged. Verification state: `docs/qubo-vod-verification.md` (blocked at writing - the unblock recipe is there).

## Global Constraints

- Same as M1/M2 (conventions, signed commits, branch `m3-memory`, no scope beyond this milestone).
- Playback goes through the same go2rtc/WebRTC pipeline as live - no second delivery path.
- Notifications derive ONLY from the MQTT event stream (client-side alerting model, per design §5) - no push infrastructure.
- **Build order fold (2026-10-16):** no live session exists this morning (no adb device attached; the stored OTP session expired). The recordings half (Tasks 1-3, 5) is HELD on a real session; the lead holds a session-window watcher and runs Task 1's probes itself in that window, handing captured bodies to the builder. Notifications (Tasks 4, 6) build FIRST - every payload shape they need is captured in fixtures already.

## Review Focus

1. **VOD verification is Task 1 for a reason**: every recording type in Tasks 2-3 must be written against captured shapes, not the decompile - if Task 1 cannot run (no phone/session), STOP and report rather than coding against guesses - Task 1.
2. **Clip-list source honesty**: the app's own metadata cache is client-side; the server must learn the real clip-listing source (Task 1 discovers it) or state plainly that only day-level browsing is possible - Tasks 1-2.
3. **VOD stream lifecycle**: playback sessions must release on player exit and on idle; a leaked VOD session burns a camera session slot - Task 3.
4. **Notification storms**: motion events burst - the event store coalesces per camera (one entry per motion episode, max one push per camera per 30s) - Task 4.
5. **Snapshot absence**: many events will have no image - the UI must look intentional without one (icon + text), not broken - Task 6.

- AQI env override landed as its own commit (789d0b0): `NAZAR_AQI_ALERT_AT`, default 60; a non-numeric value warns and keeps the default rather than refusing to boot.
- Task 2 deviations (9523d6d): `recorded_days` returns the wire's own DD-MM-YYYY strings; `Clip` is `{id, start_ms, snapshot_url}` (the plan's `duration_ms`/`path` have no source on disk). Clip segments come from a dedicated motion episodes store (one persisted ledger, logical day-keying with the day filter at read, 30s coalescing kept, `NAZAR_EPISODE_RETENTION_DAYS` default 30 with retention dropping whole days at the boundary) - deliberately NOT the notification ring, so an aged or cleared bell cannot blank the timeline; a corrupt ledger is preserved as .bak rather than overwritten. Day math is hand-rolled (`days_from_civil` + fixed +05:30) with known-value tests; the comment names the constraint that the calendar timezone param and this math move together.
- Task 3 deviations (eac658d): `expires_in` in the playback response is the idle window (120s, matching live streams) - the only expiry the server enforces, since the cloud session's own lifetime is unmeasured (live-stream analogy: it may die ~40s after the last consumer, so the player must re-ask on resume/stall like the live tile's recovered path - Task 5's requirement). The VOD stream rides the same nazar ffmpeg template as live (one delivery path) - a re-encode of already-h264; the copy path is a small follow-up if hub cost ever shows. `SupervisorError::VodUnavailable` and its M1 stub test are removed (removed code is removed); the proxy now admits `vod-<camera>` sources for known cameras, shape-checked as before. `ensure_vod` releases through the same claim-under-lock path as the reaper, so a seek racing a release ends either with the new session or with none - never a deleted stream under a live player.
- Review folds (2026-10-16): snapshot JPEGs prune with their markers (retention/eviction removes the file); the WS announce fires before the still resolves (the bell rings promptly, the still attaches after); the exact-30s coalescing boundary is pinned on both stores so they provably agree; env parsing has config-level tests; the coalesced bell path skips its save (a lost `at` bump is cosmetic); unknown /api/* paths answer 404 JSON before the SPA fallback.
